# 2주차: 추천이 잘됐는지는 어떻게 아는가

추천 시스템을 평가하는 방법을 다뤘다. 평가 방식 세 가지를 비교하고, 수업에서 주로 쓸 오프라인 평가에서 데이터를 어떻게 나눠야 하는지, 어떤 정확도 지표를 쓰는지까지 봤다.

## 평가 지표가 왜 중요한가

추천 시스템은 하나의 알고리즘이고, 같은 문제를 푸는 알고리즘은 무수히 많다. 그중 무엇이 가장 좋은지 고르려면 비교할 기준이 있어야 한다. 평가를 잘못 설계하면 좋은 모델을 과소평가하거나 그저 그런 모델을 과대평가할 수 있다.

정확도 하나만 높다고 좋은 추천도 아니다. 참신성(novelty), 신뢰도, 적용 범위(coverage), 우연성(serendipity)도 목표에 따라 중요해진다. 남들이 다 높게 평가한 인기 아이템을 추천하는 것도 좋지만, 평점이 많지 않아도 그 사람에게 딱 맞는 걸 우연히 추천해 주는 게 더 좋은 추천일 수 있다.

## 평가 방식 세 가지

### 사용자 연구 (user study)

사용자 연구는 서베이에 가깝다. 테스트 대상자를 모집하고, 추천 시스템을 써 보게 한 뒤 전후로 피드백을 받는다. 알고리즘을 바꿨을 때 사용자와 시스템의 상호작용이 어떻게 달라지는지 여러 시나리오로 볼 수 있다는 장점이 있다. 대신 응답이 그때 기분에 따라 편향되기 쉽고, 조건에 맞는 사람을 모집하는 것 자체가 비싸고 어렵다. 모집된 사람이 전체 사용자를 대표하지도 못해서 결과를 일반화하기 어렵다.

### 온라인 평가 (online evaluation)

온라인 평가는 실제로 배포된 시스템을 쓰는 실제 사용자에게서 평가를 받는다. 직접 상호작용한 결과라 사용자 연구보다 편향에 덜 취약하고, 사용자 중에서 무작위로 샘플링해 여러 알고리즘을 시험할 수 있다. 대표적인 게 A/B 테스트다.

1. 사용자를 A, B 두 그룹으로 나눈다.
2. 나이, 성별 같은 다른 조건은 같게 맞추고, 정해진 기간 동안 그룹마다 다른 알고리즘을 쓰게 한다.
3. 끝나면 유지율이나 수익 같은 목표 지표를 비교한다.

한 사람에게 두 알고리즘을 다 써 보게 하면 편향될 수밖에 없으니 그룹을 나누는 것이다. 장기적인 성능을 가장 정확하게 볼 수 있지만, 사용자가 충분히 많아야 해서 서비스 초기에는 쓰기 어렵다. 상용 시스템을 가진 쪽만 할 수 있다는 한계도 있다.

### 오프라인 평가 (offline evaluation)

오프라인 평가는 과거 데이터셋으로 평가한다. 연구와 실무에서 가장 일반적인 방식이고, 이 수업에서도 계속 이 방식을 쓴다. 데이터만 있으면 여러 설정으로 여러 알고리즘을 비교하는 표준 벤치마크로 쓸 수 있고, 여러 도메인의 데이터셋으로 일반화 가능성도 볼 수 있다.

약점은 "과거"라는 점이다. 추천은 트렌드를 따라가야 하는데 과거 데이터로는 앞으로 사용자가 어떻게 반응할지 평가하지 못한다. 장기적인 이탈이나 전환율, 우연성이나 참신성 같은 요소도 반영하기 어렵다.

## 데이터 종류가 문제를 정한다

1주차에 본 두 가지 피드백이 여기서 머신러닝 문제와 연결된다.

- 명시적 피드백(평점)으로 학습하면 연속된 값을 맞추는 회귀(regression) 문제가 된다. 1~5점이 딱 나뉘어 있으니 분류로 풀 수도 있지만 보통은 회귀로 2.7을 예측하고 3으로 보는 식으로 한다.
- 암시적 피드백(클릭했다/안 했다)으로 학습하면 1과 0을 맞히는 이진 분류(classification) 문제가 된다.

결국 협업 필터링은 분류나 회귀 문제로 일반화되고, 그래서 머신러닝의 평가 지표를 그대로 쓴다. 다만 협업 필터링만의 고유한 지표가 따로 필요할 때도 있다.

데이터는 사용자-아이템 상호작용 행렬로 표현한다. 사용자 n명, 아이템 m개면 n×m 행렬이고, 보통 행이 사용자, 열이 아이템이다. 책마다 user-item interaction matrix, utility matrix, rating matrix라고 부르는데 모두 같은 것이다. 암시적 피드백이면 값만 0과 1로 바뀐다.

## 학습 데이터와 테스트 데이터를 나누는 법

비율은 7:3이나 8:2를 많이 쓴다. 학습 데이터가 많을수록 모델이 더 많은 패턴을 보니까 테스트 비율을 굳이 늘릴 이유는 없다. 정답은 없다.

비율보다 중요한 건 나누는 방법이다. 행렬을 사용자 기준으로 잘라서 학습 데이터와 테스트 데이터가 겹치면, 모델이 학습할 때 이미 본 값을 테스트에서 맞히게 된다. 외운 걸 맞힌 거라 성능이 과대평가(overestimate)된다.

반대로 아이템(열) 기준으로 잘라서 어떤 아이템은 테스트에만 있게 하면, 모델은 그 아이템에 대해 아무 정보도 없이 맞혀야 한다. 콜드 스타트 상황을 일부러 만든 셈이라, 잘 학습된 모델도 과소평가된다.

그래서 무작위로 섞되 행과 열 어느 쪽으로 봐도 골고루 나뉘어야 한다. 어떤 사용자의 아이템 몇 개는 학습에, 나머지는 테스트에 들어가게 하고, 테스트에만 있는 아이템이라도 다른 사용자가 학습 데이터에서 매긴 평점으로 특징을 파악할 수 있어야 한다. 테스트 데이터는 수능 출제위원처럼 아무도 몰라야 한다.

## 과대평가와 과적합은 다르다

데이터를 잘못 나눠서 생기는 과대평가와 과적합(overfitting)은 구분해야 한다. 과적합은 학습 데이터로는 정확도가 99%인데 테스트 데이터로는 50%가 나오는 상황이다. 모델이 학습 데이터를 이해한 게 아니라 외워 버린 것이다. 문제와 답을 외운 학생이 숫자 하나 바뀐 문제를 못 푸는 것과 같다.

모델의 성능은 항상 테스트 데이터 기준이다. 학습 데이터에서 아무리 잘 맞혀도 의미가 없다.

과적합이 생기면 두 가지를 해 볼 수 있다.

- 데이터를 늘린다. 100개면 외우기 쉬워도 1만 개는 다 외우기 어렵다. 다만 현실에서는 데이터를 더 모으기가 가장 어렵다.
- 모델을 줄인다. 데이터에 비해 모델이 너무 크게 설계됐다는 뜻이니 레이어나 노드 수를 줄인다. 최소한의 구조로 처음 보는 데이터도 맞힐 수 있게 만드는 게 모델을 잘 만드는 것이다.

처음부터 과적합이나 과소적합을 안 겪으면 오히려 믿기 어렵다고 했다. 데이터를 다 알고 모델을 설계할 수는 없으니, 하이퍼파라미터와 구조를 바꿔 가며 맞는 모델을 찾아가는 게 보통이다.

## 검증 세트와 교차 검증

학습 중간에 잘 학습되고 있는지 보려면 검증 세트(validation set)를 쓴다. 반복이 끝날 때마다 검증 세트로 정확도를 확인하는 것이다. 사실 테스트 세트와 성격은 같다.

데이터가 수만 개 이상이면 무작위로 한 번 나눠도 결과가 안정적이다. MNIST처럼 학습용과 테스트용을 나눠 쓰면 다시 섞어도 비슷한 결과가 나온다. 그런데 데이터가 100개밖에 없으면 한 번 나눈 결과가 한쪽으로 치우칠 수 있다. 학습 데이터는 쉬운 것만, 테스트 데이터는 어려운 것만 들어갔을 수도 있다.

이럴 때 교차 검증(cross validation)을 쓴다.

1. 전체 데이터를 K개 그룹(fold)으로 나눈다.
2. 첫 번째 fold를 검증용, 나머지를 학습용으로 써서 성능을 잰다.
3. 두 번째 fold를 검증용으로 바꿔서 다시 잰다. K번 반복한다.

구조는 같지만 다른 데이터로 학습한 모델이 K개 생긴다. 보통 10개로 나누는 10-fold를 많이 쓴다. 각 fold의 성능을 보고하면 분할 운에 따른 편향을 걸러낼 수 있고, 성능이 고르게 나오면 모델 구조에는 문제가 없다고 볼 수 있다. 실제 서비스에는 하나만 써야 하니 그중 가장 좋은 걸 고르는 데 쓰기도 한다. 논문이나 프로젝트에서 모델을 만들 때는 항상 해야 한다고 강조했다.

## 회귀 문제의 지표: MSE, RMSE, MAE

평균 제곱 오차(MSE)는 실제 평점과 예측 평점의 차이를 제곱해서 테스트 데이터 개수로 평균 낸 값이다.

```
MSE = (1/|T|) Σ (r_ij − r̂_ij)²
```

r_ij는 사용자 i가 아이템 j에 준 실제 평점, r̂_ij는 모델이 예측한 평점, T는 테스트 세트다. 제곱하는 이유는 오차의 부호를 없애기 위해서다. 직관적이고 값이 낮을수록 좋다.

단점은 두 가지다. 평균을 내기 때문에 이상치에 민감하다. 100개 중 99개를 거의 맞혔어도 하나가 크게 틀리면 값이 확 커진다. 그리고 제곱했기 때문에 실제보다 높게 예측했는지 낮게 예측했는지 알 수 없어서, 모델을 어느 방향으로 고쳐야 할지 판단하기 어렵다.

MSE 값이 너무 커서 읽기 어려우니 루트를 씌운 RMSE를 가장 많이 쓴다. 의미는 MSE와 같고 이상치에 민감한 것도 같다.

평균 절대 오차(MAE)는 차이의 절대값을 평균 낸 것이다. 해석이 더 직관적이지만, 역시 높게 예측했는지 낮게 예측했는지는 알 수 없다. 보통 MSE가 떨어지면 MAE도 같이 떨어지는 패턴을 보인다.

## 분류 문제의 지표: 정밀도와 재현율

암시적 피드백처럼 참/거짓을 맞히는 문제는 혼동 행렬(confusion matrix)부터 만든다.

| | 모델: 참 | 모델: 거짓 |
|---|---|---|
| 실제: 참 | TP (맞게 예측) | FN (틀리게 예측) |
| 실제: 거짓 | FP (틀리게 예측) | TN (맞게 예측) |

이 네 개의 개수만 있으면 지표를 다 구할 수 있다.

- 정밀도(precision) = TP / (TP + FP): 모델이 참이라고 예측한 것만 본다. 추천 시스템으로 말하면 사용자가 좋아할 거라고 추천한 아이템 중 실제로 좋아한 비율이다.
- 재현율(recall) = TP / (TP + FN): 실제로 참인 것만 본다. 사용자가 실제로 좋아하는 아이템 중 모델이 맞게 찾아낸 비율이다. true positive rate라고도 한다.
- 정확도(accuracy) = (TP + TN) / 전체: 우리가 보통 말하는 정확도다.

예제로 계산해 봤다. 아이템이 0~9번까지 10개 있고, 사용자가 실제로 좋아하는 아이템은 0, 2, 5, 6이다. 모델은 2, 3, 6, 7, 8을 좋아할 거라고 예측했다.

- 정밀도: 모델이 예측한 5개 중 실제로 좋아하는 건 2와 6, 2개라서 2/5 = 0.4
- 재현율: 실제로 좋아하는 4개 중 모델이 찾은 건 2와 6, 2개라서 2/4 = 0.5

집합으로도 쓸 수 있다. 사용자 u가 실제로 상호작용한 아이템 집합을 Y_u, 모델이 예측한 집합을 Ŷ_u라고 하면 정밀도는 |Y_u ∩ Ŷ_u| / |Ŷ_u|, 재현율은 |Y_u ∩ Ŷ_u| / |Y_u|다. 다중 분류로 가면 혼동 행렬이 커질 뿐 원리는 같다.

## 회고

1주차에 회귀와 분류 이야기를 들었을 때는 데이터 종류에 따른 구분 정도로 생각했는데, 평가 지표까지 이어서 보니 연결이 확실해졌다. 평점을 예측하면 RMSE와 MAE로 보고, 클릭을 예측하면 정밀도와 재현율로 본다. 문제를 정하는 순간 쓸 지표도 정해진다.

A/B 테스트가 가장 정확하지만 사용자가 많아야 한다는 부분은 개인 프로젝트 입장에서 현실적인 이야기였다. GrowTechStack에 추천을 붙여 본다고 해도 사용자를 두 그룹으로 나눌 만큼 트래픽이 충분하지 않다면 결국 쌓아 둔 클릭 데이터로 오프라인 평가부터 하게 될 것이다. 그때는 오프라인 평가가 트렌드를 못 따라간다는 한계도 같이 안고 가야 한다. 기술 블로그 글은 시의성이 강해서 이 한계가 더 크게 느껴질 것 같다.

데이터를 행이나 열 기준으로 자르면 안 된다는 것도 기억해 둘 만하다. 아이템 기준으로 자르면 일부러 콜드 스타트를 만든다는 설명이 1주차 내용과 이어져서 이해가 잘 됐다.
